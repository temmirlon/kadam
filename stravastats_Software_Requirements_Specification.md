# Техническое задание: AI-сервис анализа тренировок из Strava

## 1. Название проекта

Рабочее название: **Strava AI Coach**

Альтернативные варианты названия:

* AI Training Coach
* Strava Coach Bot
* Endurance AI Coach
* TriCoach AI

## 2. Краткое описание проекта

Проект представляет собой backend-first сервис для автоматического анализа тренировок из Strava с помощью искусственного интеллекта.

После завершения и сохранения тренировки в Strava сервис автоматически получает данные активности, обрабатывает их, генерирует AI-анализ и отправляет пользователю отчет.

В первой версии пользователь получает отчет через Telegram-бота. При этом Telegram не является основной платформой проекта, а используется только как первый интерфейс MVP.

Архитектура должна быть построена так, чтобы в будущем к тому же backend можно было подключить:

* веб-интерфейс;
* iOS-приложение;
* email-уведомления;
* другие каналы доставки.

## 3. Контекст проекта

Автор проекта — 23-летний разработчик, проходящий Ausbildung на FIAE в Мюнхене.

Автор активно занимается бегом, велосипедом и в будущем планирует подготовку к Ironman 70.3, а возможно и к полной дистанции Ironman.

Большинство тренировок записываются в Strava. Сейчас для получения AI-анализа после тренировки нужно вручную делать скриншоты или копировать данные из Strava и отправлять их в ChatGPT, Gemini или другой AI-инструмент.

Это неудобно, долго и плохо масштабируется, если анализировать тренировки регулярно.

## 4. Основная идея

Сервис должен автоматизировать процесс анализа тренировок.

Пользователь завершает тренировку в Strava. После этого сервис сам получает уведомление о новой активности, забирает данные через Strava API, анализирует тренировку и отправляет пользователю отчет.

Главная идея:

**Пользователь тренируется → сохраняет тренировку в Strava → автоматически получает честный AI-анализ.**

## 5. Цель проекта

Создать MVP-сервис, который:

* подключается к аккаунту Strava;
* получает новые тренировки автоматически;
* загружает подробные данные активности;
* получает доступные stream-данные;
* анализирует тренировку с помощью AI;
* отправляет отчет пользователю через Telegram;
* сохраняет историю тренировок и анализов;
* имеет архитектуру, готовую к расширению на web/iOS в будущем.

## 6. Проблема

Сейчас после тренировки пользователь должен вручную:

* открыть Strava;
* посмотреть данные;
* сделать скриншоты;
* скопировать показатели;
* отправить их в AI-инструмент;
* объяснить контекст тренировки;
* ждать анализ.

Это занимает время и требует лишних действий после каждой активности.

Также ручной анализ плохо работает для истории тренировок, потому что AI обычно не видит старые активности, прогресс, повторяющиеся ошибки и общую динамику.

## 7. Решение

Сервис должен автоматически:

1. Получать событие о новой активности из Strava.
2. Загружать подробные данные тренировки.
3. Получать доступные stream-данные.
4. Обрабатывать данные и рассчитывать дополнительные метрики.
5. Передавать подготовленную сводку в AI.
6. Генерировать понятный отчет.
7. Отправлять отчет пользователю.
8. Сохранять тренировку и анализ в базе данных.

## 8. Формат MVP

Для первой версии выбран формат:

**Python backend + FastAPI + Strava API + AI API + Telegram-бот + база данных**

Telegram-бот используется как первый интерфейс, потому что он:

* быстрее всего разрабатывается;
* удобен для уведомлений;
* не требует App Store;
* подходит для личного использования;
* хорошо сочетается с Python;
* позволяет быстро проверить ценность идеи.

Важно: проект не должен быть написан как “просто Telegram-бот”. Telegram должен быть только слоем взаимодействия с пользователем.

## 9. Главный архитектурный принцип

Проект должен быть построен по принципу:

**Backend first, interface second.**

Это означает, что основная логика находится в backend:

* интеграция со Strava;
* хранение пользователей;
* хранение токенов;
* получение активностей;
* обработка stream-данных;
* расчет метрик;
* AI-анализ;
* сохранение истории;
* управление отчетами.

Telegram-бот не должен содержать основную бизнес-логику. Он должен только:

* принимать команды пользователя;
* вызывать backend/service layer;
* отправлять готовые ответы пользователю.

## 11. Основной пользовательский сценарий MVP

1. Пользователь запускает Telegram-бота.
2. Бот предлагает подключить Strava.
3. Пользователь переходит по ссылке авторизации Strava.
4. Пользователь разрешает приложению доступ к данным тренировок.
5. Backend сохраняет Strava athlete ID, access token и refresh token.
6. Пользователь завершает тренировку в Strava.
7. Strava отправляет webhook-событие на backend.
8. Backend получает ID новой активности.
9. Backend загружает подробности активности через Strava API.
10. Backend загружает stream-данные активности, если они доступны.
11. Система обрабатывает данные и рассчитывает дополнительные метрики.
12. AI генерирует отчет.
13. Отчет сохраняется в базе данных.
14. Пользователь получает уведомление и анализ в Telegram.
15. Пользователь может позже запросить старые активности и старые анализы.

## 12. Что такое webhook в рамках проекта

Webhook — это механизм, с помощью которого Strava сообщает backend, что появилась новая активность.

Webhook не присылает всю тренировку целиком. Он присылает событие, например:

```json
{
  "object_type": "activity",
  "object_id": 123456789,
  "aspect_type": "create",
  "owner_id": 987654321,
  "event_time": 1710000000
}
```

После этого backend должен использовать `object_id`, чтобы отдельно запросить подробные данные тренировки через Strava API.

## 13. Можно ли получить всю тренировку

Да, для анализа можно получить большую часть нужных данных, но не напрямую из webhook.

Схема:

```text
Webhook → activity ID → запрос деталей активности → запрос streams → анализ
```

Система должна получать:

* основные данные активности;
* подробные stream-данные, если доступны;
* дополнительные показатели, рассчитанные backend-ом.

Однако часть данных может отсутствовать, если:

* устройство не записывало пульс;
* не было датчика каденса;
* не было power-данных;
* GPS скрыт настройками приватности;
* активность была записана с ограниченным набором данных.

## 14. Функциональные требования MVP

### 14.1. Telegram-бот

Telegram-бот должен выполнять роль первого пользовательского интерфейса.

Минимальные команды:

* `/start` — приветствие и краткое описание сервиса;
* `/connect_strava` — подключение Strava-аккаунта;
* `/last` — показать последний анализ;
* `/activities` — показать последние активности;
* `/help` — показать список команд.

Дополнительно можно добавить:

* `/status` — проверить подключение Strava;
* `/delete_data` — удалить сохраненные данные пользователя;
* `/reanalyze` — повторно сгенерировать анализ последней тренировки.

### 14.2. Авторизация через Strava

Система должна поддерживать OAuth 2.0 авторизацию через Strava.

Backend должен сохранять:

* Strava athlete ID;
* Telegram user ID;
* access token;
* refresh token;
* срок действия access token;
* scopes;
* дату подключения.

Система должна уметь обновлять access token через refresh token.

### 14.3. Получение новых активностей

Система должна принимать webhook-события от Strava.

При получении события backend должен:

* проверить тип объекта;
* проверить тип события;
* убедиться, что событие относится к активности;
* получить activity ID;
* проверить, не была ли эта активность уже обработана;
* поставить активность в очередь обработки.

### 14.4. Получение деталей активности

Для каждой новой активности система должна получить основные данные:

* ID активности;
* название;
* тип спорта;
* дата и время;
* дистанция;
* elapsed time;
* moving time;
* средняя скорость;
* средний темп;
* максимальная скорость;
* набор высоты;
* средний пульс;
* максимальный пульс;
* средняя каденция;
* средняя мощность, если доступна;
* калории, если доступны;
* laps/splits, если доступны;
* ссылка на активность в Strava.

### 14.5. Получение stream-данных

Система должна попытаться получить подробные данные по ходу тренировки:

* time;
* distance;
* heartrate;
* velocity_smooth;
* altitude;
* cadence;
* watts;
* moving;
* grade_smooth;
* latlng.

Если часть данных отсутствует, система должна продолжить работу и указать в анализе, что некоторые выводы ограничены из-за нехватки данных.

### 14.6. Предобработка данных

Перед отправкой данных в AI система должна подготовить структурированную сводку.

Backend должен рассчитать:

* средний темп;
* темп по километрам;
* разницу между первой и второй половиной тренировки;
* изменение пульса по ходу тренировки;
* стабильность темпа;
* стабильность пульса;
* возможный cardiac drift;
* участки ускорения;
* участки замедления;
* остановки;
* подъемы и спуски;
* соотношение темпа и пульса;
* признаки усталости;
* интенсивность тренировки.

Сырые stream-данные не должны полностью отправляться в AI без обработки. Система должна сначала агрегировать их, чтобы анализ был дешевле, быстрее и точнее.

### 14.7. AI-анализ

AI должен генерировать отчет на русском языке.

Отчет должен быть:

* честным;
* прямым;
* понятным;
* полезным для любителя бега, велосипеда и триатлона;
* без медицинских диагнозов;
* без чрезмерной мотивационной воды.

AI-анализ должен включать:

* краткое резюме тренировки;
* общую оценку;
* что получилось хорошо;
* что стоит улучшить;
* анализ темпа;
* анализ пульса;
* анализ нагрузки;
* анализ стабильности;
* возможные причины просадок;
* рекомендации на следующую похожую тренировку;
* предупреждение о недостатке данных, если данных мало;
* итоговый честный вывод.

### 14.8. Отправка уведомления

После генерации анализа пользователь должен получить Telegram-сообщение.

Сообщение должно содержать:

* название активности;
* дату;
* тип тренировки;
* дистанцию;
* время;
* средний темп;
* средний пульс, если доступен;
* краткий вывод;
* полный AI-анализ;
* ссылку на активность в Strava.

### 14.9. История тренировок

Система должна сохранять историю активностей и анализов.

Пользователь должен иметь возможность:

* посмотреть последние активности;
* открыть последний анализ;
* открыть анализ конкретной активности;
* повторно сгенерировать анализ;
* удалить свои данные.

## 15. Нефункциональные требования

### 15.1. Надежность

Система не должна падать, если:

* Strava прислала webhook несколько раз;
* access token истек;
* refresh token нужно обновить;
* у активности нет пульса;
* у активности нет GPS;
* у активности нет cadence;
* у активности нет power;
* AI API временно недоступен;
* Telegram API временно недоступен;
* база данных временно недоступна.

### 15.2. Безопасность

Секреты нельзя хранить в коде.

Нужно использовать переменные окружения или `.env` для:

* Strava client ID;
* Strava client secret;
* Telegram bot token;
* AI API key;
* database URL;
* webhook secret/verify token.

### 15.3. Приватность

Тренировочные данные являются личными данными.

Система должна:

* хранить только необходимые данные;
* не публиковать данные без разрешения;
* не отправлять GPS-данные в AI без необходимости;
* позволять удалить данные пользователя;
* не логировать access token и refresh token;
* аккуратно работать с геолокацией.

### 15.4. Масштабируемость

MVP рассчитан на одного пользователя, но архитектура должна позволять в будущем добавить нескольких пользователей.

Для этого нужно сразу хранить данные с привязкой к `user_id`.

### 15.5. Расширяемость интерфейсов

Система должна быть построена так, чтобы Telegram можно было заменить или дополнить другим интерфейсом.

В будущем должны быть возможны:

* web dashboard;
* iOS-приложение;
* email-отчеты;
* push-уведомления;
* weekly reports.

## 22. Критерии готовности MVP

3. Backend может обновлять Strava access token.
4. Strava webhook успешно доходит до backend.
5. Backend получает ID новой активности.
6. Backend загружает детали активности.
7. Backend загружает stream-данные, если они доступны.
8. Система рассчитывает базовые метрики.
9. AI генерирует текстовый анализ.
10. Пользователь получает анализ в Telegram.
11. Активность сохраняется в базе данных.
12. Анализ сохраняется в базе данных.
13. Пользователь может запросить последний анализ.
14. Пользователь может посмотреть последние активности.
15. Повторный webhook не создает дубликат анализа.

## 23. Пример формата AI-отчета

```text
🏃 Тренировка: Morning Run
📅 Дата: 12.06.2026
📏 Дистанция: 8.2 км
⏱ Время: 45:10
⚡ Средний темп: 5:30/км
❤️ Средний пульс: 154 bpm

Краткий вывод:
Хорошая аэробная тренировка средней интенсивности. Темп был достаточно стабильный, но во второй половине заметен рост пульса при похожем темпе. Это может говорить о накоплении усталости, недостаточном восстановлении или жаркой погоде.

Что хорошо:
- Ты не начал слишком быстро.
- Темп оставался относительно ровным.
- Не было резкого провала в конце.

Что стоит улучшить:
- Пульс во второй половине вырос сильнее, чем хотелось бы.
- Если цель была легкая пробежка, интенсивность могла быть чуть высокой.
- Стоит следить за восстановлением перед следующей интенсивной тренировкой.

Анализ темпа:
Первая половина была немного быстрее второй. Просадка не критичная, но она есть.

Анализ пульса:
Пульс постепенно рос, несмотря на похожий темп. Это может быть признаком cardiac drift.

Рекомендация:
Следующую похожую пробежку начни на 5–10 секунд/км медленнее и посмотри, получится ли удержать пульс стабильнее.
```

## 24. Ограничения и риски

### 24.1. Ограничения Strava API

Strava API имеет лимиты запросов. Поэтому система не должна постоянно опрашивать API.

Нужно использовать webhook для новых активностей и делать запросы только при необходимости.

### 24.2. Неполные данные

Не каждая тренировка содержит все данные.

Система должна корректно работать без:

* пульса;
* GPS;
* мощности;
* каденса;
* высоты;
* splits;
* laps.

### 24.3. Качество AI-ответов

AI может ошибаться. Поэтому анализ должен быть представлен как спортивная рекомендация, а не как медицинский или профессиональный диагноз.

### 24.4. Приватность GPS

GPS-данные могут раскрывать дом, работу или регулярные маршруты пользователя.

В MVP нужно избегать отправки точных координат в AI, если они не нужны для анализа.

### 24.5. Зависимость от внешних сервисов

Проект зависит от:

* Strava API;
* Telegram API;
* AI API;
* хостинга.

При ошибках внешних сервисов система должна сохранять статус ошибки и не терять активность.

## 29. Кроссплатформенность и гибкость разработки

Проект должен быть удобен для разработки как на Windows, так и на macOS.

Автор проекта использует обе операционные системы, поэтому окружение разработки должно быть максимально одинаковым, воспроизводимым и не зависящим от конкретной машины.

Главный принцип:

**Сначала быстро получить рабочий MVP локально, затем постепенно привести окружение к production-ready виду через Docker.**

## 29.1. Стратегия окружения

Разработка делится на несколько этапов.

### Этап 1: Локальная разработка без Docker

На первом этапе проект запускается напрямую через Python virtual environment.

Цель этапа — как можно быстрее реализовать главный flow:

```
Strava OAuth → получение активности → обработка данных → AI-анализ → Telegram-уведомление
```

Локальный стек:

```
Python 3.12+
FastAPI
SQLite
.env
Telegram Bot
Strava API
AI API
```

На этом этапе Docker не является обязательным для запуска проекта.

## 29.2. Этап 2: Docker-ready структура

Даже если проект сначала запускается без Docker, структура должна быть подготовлена так, чтобы Docker можно было добавить без переписывания архитектуры.

Для этого необходимо:

- не использовать абсолютные пути;
- хранить конфигурацию в `.env`;
- не хранить секреты в коде;
- разделить backend, bot, database и background processing логически;
- использовать единый способ установки зависимостей;
- иметь понятный `README.md`;
- подготовить `.env.example`;
- не завязывать бизнес-логику на локальное окружение.

## 29.3. Этап 3: Docker Compose

После того как основной flow заработает, в проект добавляется Docker Compose.

Цель Docker Compose — обеспечить одинаковый запуск проекта на:

- Windows;
- macOS;
- Linux;
- сервере.

Планируемая схема Docker Compose:

```
docker-compose.yml
  backend
  database
  worker
  redis
```

На MVP-этапе `worker` и `redis` могут отсутствовать. Они добавляются позже, когда появится полноценная очередь обработки тренировок.

## 29.4. Этап 4: Production-ready окружение

Для будущего деплоя проект должен быть готов к запуску в контейнерах.

Планируемый production-стек:

```
FastAPI backend
PostgreSQL
Redis
Background worker
Telegram Bot
Strava Webhook endpoint
AI API integration
```

В production окружении SQLite заменяется на PostgreSQL.

## 29.5. Windows/macOS требования

Проект должен запускаться на Windows и macOS без изменения кода.

Для этого:

- пути должны строиться через `pathlib`;
- настройки должны читаться из переменных окружения;
- зависимости должны устанавливаться одной командой;
- команды запуска должны быть описаны в `README.md`;
- база данных на первом этапе должна быть простой для локального запуска;
- код не должен зависеть от shell-специфичных команд.

## 29.6. Работа с путями

В коде запрещено использовать абсолютные пути вида:

```
C:\Users\Username\project\data
/Users/username/project/data
```

Для путей нужно использовать `pathlib`.

Пример:

```
from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent.parent
DATA_DIR = BASE_DIR / "data"
```

## 29.7. Конфигурация через .env

Все настройки проекта должны храниться в переменных окружения.

Локально используется файл `.env`.

Пример `.env`:


Файл `.env` не должен попадать в Git.

В репозитории должен быть `.env.example` без настоящих секретов.
